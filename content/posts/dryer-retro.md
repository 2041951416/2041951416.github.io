毕设做的是智能烘干机：单片机采集温湿度，控制加热和风机，把农作物烘干到目标含水率。听上去是个标准的控制系统题目，实际做下来，真正花时间的部分跟"控制"关系不大。

## 系统长什么样

```text
        ┌──────────┐
  温湿度 │ DHT22 /  │
  传感器 │ SHT30    │
        └────┬─────┘
             │ I²C / 单总线
        ┌────▼──────────┐      ┌──────────┐
        │   STM32       ├─────▶│ 继电器   │──▶ 加热管
        │   主控        │      └──────────┘
        │               ├─────▶│ MOS 驱动 │──▶ 风机
        │               │      └──────────┘
        │               ├─────▶  OLED 显示
        └───────┬───────┘
                │ USART
           ┌────▼─────┐
           │ 上位机   │
           └──────────┘
```

采集 → 判断 → 执行，一个很典型的闭环。控制律用的是最朴素的带死区的开关控制：温度低于下限开加热，高于上限断电，中间保持。

## 三件当时不懂的事

### 一、传感器读数抖动，很多时候不是传感器的问题

一开始温度读数一直在跳，±2°C 地抖。我以为是 DHT22 太差，换了一个还是抖。

实际原因有三层：

1. **采样位置** — 传感器贴在加热管附近，风没吹到它，测的是局部气温
2. **没有滤波** — 单次采样直接参与判断，噪声全部进去
3. **供电同源** — 传感器和继电器共用一路 5V，继电器吸合瞬间电压跌落，读数跟着跳

改了采样位置（放到回风口）、加了滑动平均、给继电器单独走一路电源并加去耦之后，抖动降到 ±0.3°C。

**结论：数字传感器的读数问题，先怀疑供电和物理安装，再怀疑器件本身。**

```c
// 8 点滑动平均，够用且不占多少算力
#define N 8
static float buf[N];
static uint8_t idx;

float filter(float x) {
    buf[idx] = x;
    idx = (idx + 1) % N;
    float sum = 0;
    for (int i = 0; i < N; i++) sum += buf[i];
    return sum / N;
}
```

### 二、继电器驱动电机的干扰，是"死机"的主要原因

现象：风机启动的瞬间，屏幕花屏、单片机偶尔复位。

我一开始以为是程序跑飞了，加了看门狗，结果变成"频繁重启"。

真正的原因是**感性负载的反电动势**。风机是感性负载，断电瞬间产生的尖峰通过电源线传导回来，把 MCU 的供电拉下去。

解决：

- 风机两端并续流二极管 + RC 吸收
- 继电器线圈加续流二极管（这个我漏了，是最低级的错误）
- MCU 供电和负载供电分开，中间加磁珠和电解电容

**结论：控制类项目里，干扰源几乎总是电机和继电器。先给它们加吸收，再谈软件健壮性。**

### 三、"闭环"不等于"自动"

我原本的设计是：检测到温度低于目标就开加热。第一版跑起来之后发现，系统会在目标温度附近高频开关，加热管寿命堪忧，温度也在抖。

后来加了**死区**和**最小开关间隔**：

```c
#define T_TARGET   60.0f
#define T_HYST      2.0f   // 回差 2°C
#define MIN_TOGGLE  5000   // 最小 5 秒间隔

static uint32_t last_toggle = 0;
static bool heating = false;

void control(float t) {
    uint32_t now = HAL_GetTick();
    if (now - last_toggle < MIN_TOGGLE) return;

    if (!heating && t < T_TARGET - T_HYST) {
        heating = true;  last_toggle = now; relay_on();
    } else if (heating && t > T_TARGET + T_HYST) {
        heating = false; last_toggle = now; relay_off();
    }
}
```

这是最原始的方法，但它比 PID 更适合这个场景：**对象有大滞后、执行器只有开关两种状态**，PID 的连续输出在这里没有意义。

**结论：控制算法要和执行器匹配。开关执行器配开关控制（带回差），别硬套 PID。**

## 如果重做

按现在知道的东西，会这样改：

1. **先做电源和地，再做信号**。第一版把继电器、风机、MCU 混在一块两层板上，后来返工花了比画板还多的时间。
2. **每个外设单独验证**。第一版是整机一起调，出问题时无从下手。现在会先把 GPIO、I²C、USART 一个个点亮。
3. **留测试点**。电源、关键信号、地，全部引到测试焊盘上。调试时省下的时间远超画板时多花的十分钟。

还有一条不算技术：**早点开始画板**。我花了三周调代码，留给 PCB 和打样返工的时间只有十天，最后是靠熬通宵补上的。

## 收获

这个项目技术上不难，但它是我第一次把"传感器 + 控制 + 执行器 + 显示 + 通信"完整串起来，也是第一次为一块自己画的板子调 bug。

真正学到的是**排查顺序**：电源 → 时钟 → 复位 → 代码。之前我是反着来的，先在代码里找问题，找了半天发现是焊点虚了。
